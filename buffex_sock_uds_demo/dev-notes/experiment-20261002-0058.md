# `buffex_uds_comp_experiment` 落地记录：跨进程 TCP/UDS × 两个适配器

日期：2026-10-02 00:58
涉及：`buffex_uds_comp_experiment`（全 crate）；只读参考 `buffex_tokio_adapt` /
`buffex_compio_adapt` / `buffex`（**未改动**）
前置：人类指示——「用 `buffex_tokio_adapt` 和 `buffex_compio_adapt` 分别作为两个
进程的通信底座，用 TCP socket 和 unix domain socket 分别通信，必须使用两个
crate 提供的 `BuffRead` / `BuffWrite` 作为 IO 收发 API，并分别做 benchmark」。

## 1. 目标与验收口径

| 要求 | 落地方式 |
| --- | --- |
| 两个进程 | `peer_tokio` 与 `peer_compio` 两个独立进程，由 `bench_harness` 拉起 |
| 两个适配器各自作底座 | tokio 进程只用 `buffex_tokio_adapt`，compio 进程只用 `buffex_compio_adapt` |
| TCP 与 UDS | `--transport tcp|uds`，双向都跑（谁发谁收都覆盖） |
| 必须用 `BuffRead`/`BuffWrite` | 对端设备 IO 全部由适配器承担；业务代码只经 `TrBuffRead` / `TrBuffWrite` 借段搬字节，`src/pump.rs` 里没有一行 socket 读写 |
| 分别 benchmark | `bench_harness` 跑 2 传输 × 2 方向 × 3 粒度（吞吐）+ 2 传输 × 2 方向 × 2 粒度（RTT），出 markdown 报告 |

## 2. 关键技术决策

### 2.1 依赖统一：`[patch]` 把 git 源的 `buffex` 换成同仓路径

冲突点：`buffex_tokio_adapt` 依赖 **git** 的 `buffex`（`dev/0.3.0`），而
`buffex_compio_adapt` 依赖 **本地路径** `../buffex`（它需要 `close` 一族，见
`buffex_compio_adapt/Cargo.toml` 里的待办注释）。两者**同名同版本不同源**，一旦
进入同一个 workspace 的解析图，Cargo 会因锁文件冲突直接失败（一个包名只能有
一个来源）。

做法：实验 crate 里加

```toml
[patch."https://gitee.com/lino_snsalias/buffex.git"]
buffex = { path = "../buffex" }
```

效果与代价：

* 整张依赖图里只剩一份 `buffex`，两个适配器**共用同一个 `Ring`**；
* 实验代码因此能写一份泛型收发泵同时喂两边（`TrBuffRead` / `TrBuffWrite` 与段
  类型都来自同一个 `abs_buff`）；
* 代价是要求本地路径版 `buffex` 是 git `dev/0.3.0` 的**超集**。实测成立：
  `cargo check --all-targets` 通过，`buffex_tokio_adapt` 也未受影响。
* `[patch]` 只在实验 crate 自己的 workspace 里生效，**不影响**其它 crate 的解析。

### 2.2 进程形态：3 个 bin + 1 个共享库

`peer_tokio` / `peer_compio` / `bench_harness` 三个 bin 共享 `src/lib.rs`：

* 差异只在「怎么建连接、怎么构造适配器」（约 200 行 × 2）；
* 协议、校验和、收发泵、计时口径、指标结构、报告渲染只写一份；
* `bench_harness` 不碰业务字节，因此「三个进程」不引入额外的数据路径。

### 2.3 `FinishWrite`：把「收尾」从 `TrBuffWrite` 里补出来

两个适配器的收尾入口同名（`flush_async` / `close_async`）但类型不同（tokio 按需
推进、compio 等后台泵），且都**不属于** `TrBuffWrite`。为了让 benchmark 主体保持
泛型，实验里定义了一个内部小 trait `bench::FinishWrite`（`flush_ring` /
`close_ring`）。

实现放在**定义 trait 的 crate**（`src/finish.rs`）而不是两个 bin 里：bin 是独立
crate，对「外部类型 + 外部 trait」组合写 impl 会撞孤儿规则（实测报 E0117），只有
在定义 trait 的 crate 里写才合法。

### 2.4 协议与对账

* 吞吐：`[8 字节小端总长][负载]`，收端据此知道边界；发送端收尾用 `close`（等同
  `shutdown`），收端的 EOF 由适配器合成为 `Closing`。
* RTT：定长 `chunk` 字节的消息乒乓，不带头部（省掉每轮分帧开销）。
* 对账：两侧各自对负载做**按 `u64` 分组回绕累加**的滚动校验和（不是逐字节 FNV，
  避免校验和本身成为瓶颈）。编排器要求「两侧校验和一致 + 字节数一致」才判 ok。

### 2.5 结果传递：扁平 JSON 行 + 手写解析器

每个对端结束时打一行 `{"event":"result",...}`，编排器读 stdout 汇总；不引
`serde`。踩了两个坑，都写成了用例（`tests/proto_.rs`）：

1. **数字不能先过 `f64`**：`u64` 校验和（如 `0xdead_beef_cafe_f00d`）超出 `f64`
   的 53 位精度，`JsonValue::Num` 必须保留原始文本，取用时再按整数或浮点解析；
2. **字符串要按字节收集再转 UTF-8**：逐字节 `as char` 会把多字节字符拆坏
   （往返后 `note` 变乱码）。

## 3. 实验最重要的发现：`read_async` 只在「环段被填满」或「设备结束」时交付数据

### 3.1 现象

第一版把 RTT 做成最自然的乒乓：客户端写一条 → `flush` → 读回显；服务端读一条 →
回显 → `flush`。结果：

* 三种组合（tokio↔tokio、tokio→compio、compio→tokio）**全部挂死**；
* toy 用例里 tokio 侧的服务端进程 100% CPU 空转（`utime/stime` 每秒都在涨）。

### 3.2 排查过程（含一次「污染-还原」）

1. 先在 `buffex_tokio_adapt/src/write_.rs` 的 `pump_` / flush 里临时加 `eprintln!`
   打印（`BUFFEX_DBG=1` 门控）。看到：`try_read` 拿到了段、`data_size=4096`，但
   `move_items_into_output_async` 返回 **`Both(0, BrokenPipe)`**。
2. 该打印已用 `git restore --source=HEAD -- src/write_.rs` **完整还原**；该 crate 里
   只剩一条**本来就存在**的未提交改动（`Cargo.toml` 里 `mm_ptr` 的 path→git），
   与本轮无关、未触碰。
3. 换用「内存 socket + 延迟写 + 短窗口观察」的确定性探针（现固化为
   `tests/read_semantics_.rs`），一举把语义钉清楚：

| 场景 | tokio 侧 | compio 侧 |
| --- | --- | --- |
| 环容量 == 可用数据（如都 4 KiB） | 及时交付 | 及时交付 |
| 环容量 64 KiB、只有 4 KiB 可用且设备未结束 | 600 ms 窗口内**不交付** | 600 ms 窗口内**不交付** |
| `try_read`（poll-once） | 能拿到 4 KiB 部分数据 | — |

结论：两个适配器的搬运泵都以「**一个可写环段被填满**」为一次搬运的终点
（tokio 侧 `pump_` 用 `Demand::no_more_than(room)`、compio 侧后台泵同理），
所以当设备上只有一条小消息、对端又不会再补数据时，`read_async` 会一直 park 在
「等环段填满」上。乒乓 RTT 正好踩中这一点：**一条消息填不满环段 ⇒ 双方互等**。

`try_read` 之所以能拿到部分数据：它只 `poll_once_` 推一轮同步搬运，随后**丢弃**
那个 future，段按已搬入量提交（`advance_write`），于是数据进了环、可以被借出。

### 3.3 处置

* RTT 模式把硬约束写进 CLI：**`--ring-cap` 必须等于 `--chunk`**（一条消息恰好
  填满一个环段），不满足直接报错并说明原因；`plan_cases` 里 RTT 用例自动这么传。
* 单向吞吐不受影响（发送端持续灌数据，收尾 `close` 让收端看到 EOF，EOF 本身也是
  交付路径）。
* 把语义固化成 5 条特征测试（`tests/read_semantics_.rs`，含中文文档注释）。其中
  「环段未填满不交付」两条是**故意断言当前限制**：若上游将来改成「有数据就交付」，
  它们会失败——那正是放宽 `ring-cap == chunk` 的提示。

### 3.4 顺带发现（本实验不改其他 crate，仅备案）

`buffex_tokio_adapt::BuffWrite::pump_` 里：

```rust
if moved.contains_left() || !moved.contains_right() {
    return true;
}
```

当搬运结果是 `SomeOf::Both(0, err)`（一个字节都没写出、同时带设备错误）时，
`contains_left()` 为真 ⇒ 返回 `true` 且**不把错误记进 `err_`**；于是
`flush_async` 的 `while pump_().await {}` 永远退出不了，表现为 100% CPU 空转，
并且真实的设备错误被吞掉。我们在「对端已退出、服务端仍回写」时观察到 EPIPE 被
这样吞掉。建议上游把 `Both(0, err)` 也记进错误槽（或让 `contains_left()` 的判据
带上「至少搬了 1 个」）。本实验只做编排层超时兜底，不动别人的代码。

## 5. 追加：`raw` 直连对照组（第二轮）

人类追加指示：「增加一个对照组，即不使用 buffex 相关的 crate，直接 tokio 对 compio
的收发测试和性能数据，并且运行逻辑要与带有 buffex 相关的测试代码相同。」

### 5.1 形态：同一个二进制 + `--backend buffex|raw`

没有另起两个对端二进制，而是给现有对端加了 `--backend` 开关。理由是「运行逻辑要
相同」这条要求本身：连接建立、协议、握手、计时窗口、校验和、结果结构、编排器全部
复用，唯一分叉点是 `run_split_` 里「构造适配器」还是「包一层直连设备」。

代价是 raw 路径所在的可执行文件仍然链接了 buffex crate。为保证「不使用 buffex」这条
语义是**代码层面**成立的，对照组的实现整个放在 `src/raw.rs`：该模块**不 import 任何
`buffex*` / `abs_buff*` crate**，只用 `tokio::io` / `compio::io` 与实验自己的
proto/checksum/metrics。`tests/e2e_.rs` 里还用一条用例（`raw_and_buffex_agree_on_payload_`）
断言两组对同一负载给出**相同校验和**，证明两组搬的是同一串字节、可以直接对比。

### 5.2 用两个小 trait 抹平 API 差异

`RawRead`（读一次 + 暴露最近一次读到的字节）与 `RawWrite`（整块写 + flush +
shutdown）把 tokio 与 compio 的差异挡在四个 benchmark 主体之外，主体只写一份。

一个必须正面处理的差异：**compio 只能拿拥有型缓冲**（`AsyncWriteExt::write_all<T:
IoBuf>`、`AsyncRead::read<B: IoBufMut>`），而 `&'static` 之外借来的切片不满足
`IoBuf`。对照组因此把写接口设计成

```rust
fn write_all_owned(&mut self, buf: Vec<u8>) -> impl Future<Output = Result<Vec<u8>, String>>;
```

即「**把缓冲交出去、再拿回来**」：tokio 侧借出去写、原样还回；compio 侧把同一个
`Vec` 送进驱动再取回。稳态既不额外拷贝、也不额外分配，`bench_send` 里就是
`payload = tx.write_all_owned(mem::take(&mut payload)).await?` 这样的循环。

读侧同理，另外踩准了一个细节：`Vec<u8>` 的 `IoBufMut::as_uninit()` 长度等于
**capacity**，驱动读完会通过 `SetLen` 把 `len` 设成实际字节数。因此只要让「capacity
恰好等于本次请求窗口」，就能一次分配、之后每轮复用，既不用 `resize` 抹零、也不用
再拷一遍（`CompioRead` 就是这么做的）。

### 5.3 口径对齐

* 对照组忽略 `--ring-cap`（没有环），RTT 的「`ring-cap == chunk`」硬约束只对 buffex
  组生效（`cli::parse_peer_args` 按后端区分）；`plan_cases` 也据此分别填字段；
* 计时窗口、负载模式、8 字节总长头部、校验和算法、`PeerResult` 字段全部与 buffex 组
  共用同一份实现，报告里只多一列「后端」；
* `runner` 会核对对端**自报的 backend** 与用例要求是否一致，防止跑到过期二进制。

## 6. 结果摘要与解读

见 `results/bench-final.md`（同目录 `.jsonl` 为原始记录；跑法：40 个用例 ×
`--repeats 3` 取最好成绩，**全部 ok、校验和全部一致**）。

### 6.1 单向吞吐（MiB/s，取最好成绩）

| 传输 | 粒度 | 方向 | buffex 环 | 直连（对照） | 对照 / buffex |
| --- | --- | --- | ---: | ---: | ---: |
| tcp | 4 KiB | tokio → compio | 235.6 | 516.4 | 2.19× |
| tcp | 4 KiB | compio → tokio | 698.2 | 215.5 | 0.31× |
| tcp | 64 KiB | tokio → compio | 729.8 | 1751.3 | 2.40× |
| tcp | 64 KiB | compio → tokio | 749.3 | 1292.5 | 1.72× |
| tcp | 256 KiB | tokio → compio | 908.9 | 1623.4 | 1.79× |
| tcp | 256 KiB | compio → tokio | 805.1 | 1646.6 | 2.05× |
| uds | 4 KiB | tokio → compio | 592.7 | 355.0 | 0.60× |
| uds | 4 KiB | compio → tokio | 860.1 | 330.6 | 0.38× |
| uds | 64 KiB | tokio → compio | 945.1 | 1894.6 | 2.00× |
| uds | 64 KiB | compio → tokio | 1146.3 | 1637.4 | 1.43× |
| uds | 256 KiB | tokio → compio | 977.1 | 1636.6 | 1.68× |
| uds | 256 KiB | compio → tokio | 1090.1 | 1736.5 | 1.59× |

读法：

* **中大粒度（64 KiB / 256 KiB）：直连普遍快 1.4×–2.4×**。这一段里系统调用次数不是
  瓶颈，buffex 组多出来的「设备 ↔ 环」搬运（compio 侧还必须过一次中转缓冲，见
  `buffex_compio_adapt` 的 crate 文档）就成了纯开销。
* **小粒度（4 KiB）：结论反转，而且取决于「谁发」**：
  * compio 发时 buffex 组反而快得多（TCP 698 vs 216、UDS 860 vs 331）。原因很可能是
    **环起到了 write coalescing 的作用**：compio 侧适配器是后台泵，按环段（≥ 一段
    可用空间）取数写设备，把多次 4 KiB 写合并成更少的系统调用；对照组每个 4 KiB
    就要一次 `write`。
  * tokio 发 + TCP 时反过来（buffex 236 vs 直连 516）：tokio 侧适配器是**按需驱动**，
    调用方每借一次段只推一轮搬运，4 KiB 就对应一次设备写，合并无从发生，环只带来了
    额外一层搬运。
  * tokio 发 + UDS 又是 buffex 更快（593 vs 355），说明收端的 compio 适配器也在
    「按环段读」，读侧的合并同样有效——UDS 的单次系统调用比 TCP 便宜，这一侧的收益
    就盖过了发端的开销。
  * 这一节的机制解释**只是最可能的一种**，要坐实需要 syscall 计数（见 §7.4）；但
    「小粒度下谁在做合并、谁在一包一次系统调用」这个观察本身是稳的，而且解释了第一轮
    报告里那条看着突兀的方向性差异。
* 传输方式之间（TCP vs UDS）没有稳定的优劣：同在直连组、同样 64 KiB 时 UDS 略快
  （1895 vs 1751），256 KiB 时两者接近。

### 6.2 往返时延（p50，1000 次往返）

| 传输 | 消息 | buffex 环（tokio / compio 作客户端） | 直连（tokio / compio） |
| --- | --- | --- | --- |
| tcp | 64 B | 80.29 µs / 79.92 µs | 67.08 µs / 68.62 µs |
| tcp | 4 KiB | 91.78 µs / 88.87 µs | 75.05 µs / 73.39 µs |
| uds | 64 B | 60.90 µs / 66.08 µs | 54.57 µs / 51.78 µs |
| uds | 4 KiB | 75.00 µs / 71.16 µs | 58.55 µs / 56.75 µs |

* 直连组 p50 低 10–25%（约 5–17 µs），量级仍是几十 µs：说明乒乓往返的瓶颈在
  「每轮一次 `flush`（一次真实 write）+ 两个进程/两个运行时之间的唤醒」，环与适配器
  只贡献了其中一小段；
* 消息从 64 B 涨到 4 KiB，两组 p50 都只涨几 µs，进一步说明瓶颈不在数据量；
* 与第一轮（只有 buffex 组）相比数值同量级，抖动在进程调度噪声范围内。

### 6.3 结论

* 「buffex 环 + 适配器」在**大块搬运**上要付出可测的额外成本（1.4×–2.4×），代价换来
  的是调用方拿到的是 `TrBuffRead` / `TrBuffWrite` 这套缓冲抽象；
* 在**小消息、高频**的场景里，环与后台泵的「合并设备写」反而可能超过直连（compio 发
  时 2–3×），也就是说适配器不是单纯的负开销，它的价值与代价都取决于负载形态；
* 两种传输方式在这份负载下没有稳定差异；RTT 主要由每轮的收尾与调度决定。

4. 可加 CPU 时间 / 系统调用次数统计（`/proc/<pid>/stat` 的 `utime/stime`、
   `perf stat -e syscalls:sys_enter_write`），把「每字节成本」与 §5 里那条
   「tokio 发 4 KiB 偏慢」的解释坐实。
