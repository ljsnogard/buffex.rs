# buffex_smol_adapt：smol 设备经 ring 接上 TrBuffRead / TrBuffWrite

> 记录本 crate 从需求到落地的完整因果链：**每个「为什么这样」都配上当时看到的事实**
> （编译错误原文、上游源码位置、实测断言结果），便于后续在别的运行时上复用这套判断。

---

## 1. 需求与出处

- **需求方**：`smux_v1` 的 `dev-notes/outlook-production-readiness-20261006-2058.md` §2.2
  ——「smol 后端实际不可用」：smux 侧没有 smol 的 feature、没有传输适配、零测试覆盖；
  而跨后端三进程实验（同文 §3.6）把「smol 装配」列为**硬前置**。
- **本 crate 的范围**：只做「设备适配 + 环适配」两层，产出一个可复用的
  `buffex_smol_adapt`；smux 侧的 feature、冒烟 target、UDS 骨架不在本次范围内。
- **参照实现**：
  - `buffex_tokio_adapt`——**按需驱动**（不 spawn）、设备层与环层同 crate；本 crate 的
    骨架与它逐项同构；
  - `buffex_compio_adapt`——同样的两层，但驱动模型是「构造即 spawn 后台泵」。

## 2. 设备 trait 选型：`futures-lite`

smol 自己不做 IO：`smol` 2.0.2 的 `lib.rs` 里

```rust
pub use { ..., futures_lite::{future, io, pin, prelude, ready, stream}, ... };
pub use { async_channel as channel, async_fs as fs, async_lock as lock, async_net as net };
```

也就是说 `smol::io` 就是 `futures_lite::io` 的重导出；`async-net` 2.0.0 的
`UnixStream` 实现的也是这一族 trait（`src/unix.rs` 的 `impl AsyncRead for UnixStream`
/ `impl AsyncWrite for UnixStream`）。因此设备边界直接取
`futures_lite::io::{AsyncRead, AsyncWrite}`，`async_net::unix::UnixStream` 无需包装，而
本 crate **不依赖 smol 本体**（与 `buffex_tokio_adapt` 不把 tokio 作为正式依赖同理）。

trait 方法是 `fn poll_read(self: Pin<&mut Self>, cx, &mut [u8])`，本 crate 只在
`R: Unpin` 时按 `Pin::new(&mut dev)` 使用，因此设备约束是 `AsyncRead/AsyncWrite + Unpin`。

## 3. 驱动模型：按需驱动，不 spawn

最终形态与 `buffex_tokio_adapt` 一致：

* **不 spawn 任何任务**，搬运挂在调用方自己的 poll 上：
  `try_read` / `try_write` 用 `poll_once_`（`Waker::noop`）同步推一轮，`read_async` /
  `write_async` 在等待条件满足的过程中持续推进，收尾用 `flush_async` / `close_async`；
* 适配器拥有设备（`BuffRead<R>` / `BuffWrite<W>`），泵每一轮借用一次，因此设备约束只有
  `Unpin`，没有 `'static`；
* 调用方因此在 `smol::block_on`、`LocalExecutor`、`async_io` 或任何自定义执行体下都能
  直接用，**不需要 `run_until`**。

### 3.1 曾尝试「内部 spawn 后台泵」，被 Send 挡回

最初的形态照 `buffex_compio_adapt` 做（构造即 spawn）。`smol::spawn` 的全局 Executor
**自带后台线程**（`smol-2.0.2/src/spawn.rs`：惰性建 `Executor`，按 `SMOL_THREADS`
（缺省 1）起线程并 `block_on(global().run(pending()))`），看起来正合适。但 `cargo check`
给出：

```text
error: lifetime bound not satisfied
   --> src/read_.rs
    |  let pump = smol::spawn(read_pump_::<R, C, SharedRingOf<C>>( ... ));
    = note: this is a known limitation that will be removed in the future
            (see issue #100013 ...)

error: higher-ranked lifetime error
    = note: could not prove `impl Future<Output = ()>: std::marker::Send`
```

**根因**：泵里调用 `abs_buff` 的 `move_items_from_input_async` /
`move_items_into_output_async`，它们生成的 future 内部持有 `TyInput::ReadAsync<'f>` 这样的
**GAT 投影**，而 GAT 投影不传递 auto trait，于是「实际 `Send`」无法被证明。
`buffex_tokio_adapt` 的 dev-notes 记录过同一现象。

**排除「专属线程」**：`std::thread::spawn` 要求闭包 `Send`，而泵 future 按类型系统不是
`Send`，连同设备、环半部一起跨不过去；在线程内部构造也不行，因为这些东西必须先跨线程
传进去。**排除 `LocalExecutor`**：那条路能编译（`spawn` 不要求 `Send`），但它把「构造
即启动」变成「调用方必须持有并驱动一个本地执行体」，与按需驱动相比只多了约束、没有
多出能力，因此最终没有采用。

**一个附带确认**：为排除「瓶颈在 ring 自己」，做过一次编译期断言实验——`Ring`、
`RingReader`、`RingWriter`、`RingReadAsync`、`RingWriteAsync`
（`B = Owned<[MaybeUninit<u8>], CoreAlloc>`、`S = Shared<Ring<B, u8>, CoreAlloc>`）
**都满足 `Send` / `Sync`**。瓶颈确实只在 GAT 投影。

### 3.2 结论

沿用 `buffex_tokio_adapt` 的按需驱动：没有 `Send` 约束、没有任何执行体依赖，公开面是
`BuffRead::try_new(dev, cap, cfg)` / `BuffWrite::try_new(dev, cap, cfg)`，与 tokio 版逐字
同形。

## 4. 零拷贝：两个方向都不经中转

| 层 | tokio 版 | compio 版 | 本 crate |
| --- | --- | --- | --- |
| 段级（环 ↔ 段搬移） | 零拷贝 | 零拷贝 | 零拷贝 |
| 写向（段 → 设备） | 零拷贝 | 必过中转 | 零拷贝 |
| 读向（设备 → 段） | 零拷贝 | 必过中转 | **零拷贝** |

* **写向**：`poll_write` 收 `&[u8]`，段的字节由调用方保证已初始化，直接借出去即可。
* **读向**：`poll_read` 收 `&mut [u8]`（要求已初始化），而段的写窗口是
  `&mut [MaybeUninit<u8>]`。本 crate **不做中转缓冲**，用
  `assume_init_bytes_mut_` 把窗口原样借给设备。

### 4.1 那一处刻意的 `unsafe`（知情决策）

严格按 Rust 引用的有效性定义，构造指向未初始化内存的 `&mut [u8]` 处于灰区（引用应指向
有效值，而「未初始化的 `u8`」不是有效值）；标准库目前也没有稳定的「未初始化读缓冲」
签名（`ReadBuf` 一类只在 nightly 的 `core_io` 里）。

本 crate 的选择是**要零拷贝**，并把这条路径压缩到一个函数里，让实际行为受三条不变式
约束：

1. 这段内存只被交给「只写」的设备（`AsyncRead::poll_read` 的契约），设备写入前没有
   任何代码读取它；
2. 设备返回 `Ok(n)` 时前 `n` 个字节必定已初始化；使用方只把前 `n` 个计入已搬入量，
   `buffex` 的段也只按该量 `advance_write`；
3. 该切片不离开当次设备调用（生命周期限制在 step 函数内部）。

取舍的理由（`smux_v1` 的实测背景）：中转方案的代价是**每一批数据多一次
「设备 → 中转 → 段」的往返拷贝**，而读路径正是大文件传输的热点；这也是本次明确选择
「该 `unsafe` 就用 `unsafe`」的原因。若上游将来提供未初始化读缓冲的签名，本函数应当被
整体替换掉。文档与注释都写明了这一点，避免后来者把它当成普通的安全封装。

## 5. EOF 与设备违约的翻译

- **读向**：`abs_buff` 的输入搬移不允许「返回 0 个且无错误」（内层
  `assert!(cc > 0 || x.contains_right())`），而 `poll_read` 用 `Ok(0)` 表示 EOF。
  设备层把 `Ok(0)` 翻成 `TaggedError(io::ErrorKind::UnexpectedEof, ReadErrTag::Closing)`；
  适配器把 `Closing` 认作「设备正常结束」（只置 `eof_`，不进错误槽），并在**环被取空**
  之后把 `ConsumerError::Drained` 合成为 `ConsumerError::Closing`。
- **写向**：非空缓冲上的 `Ok(0)` 是设备违约。`abs_buff` 的输出搬移对它同样会空转
  （`buffex_tokio_adapt` 的 `ZeroWriteAsErr` 记录了这条），因此在**设备边界**就翻成
  `io::ErrorKind::WriteZero`。因为翻译发生在设备层，本 crate **不需要**
  `ZeroWriteAsErr` 那层设备包装。

## 6. 写端不空转的三条保证

沿用 `buffex_tokio_adapt` 在 `2026-10-02` 实验后定下的规则（本 crate 逐条复用）：

1. `pump_` 的返回值只表示「真的向设备交付了至少 1 个字节」，`SomeOf::Both(0, err)` 不算
   进展；
2. 任何带错误的结果都先记进 `err_`（含 `Both(n, err)`），设备错误不允许被吞掉；
3. 收尾循环遇到「环里还有数据、但一整轮零字节交付且设备未报错」时记一条 `WriteZero`
   并终止。

## 8. 遗留与后续

1. **接入 smux_v1**（下一步，不在本 crate 内）：加 `test-smol-runtime` feature + 一个
   smol 的 UDS 冒烟 target。因为不走 spawn，smux 侧的装配只需把设备换成
   `async_net::unix::UnixStream`，不需要任何执行体配套。
2. `format_use_imports.py --check` 全绿：`x_deps` 里重复的 `buffex` 根合并成
   `pub use buffex::{self, x_deps::abs_buff};`（另两个 adapt crate 还是旧的两行写法，
   待统一）。**踩坑记录**：该脚本的 `--fix` 在这种块上做过破坏性改写——把
   `pub use futures_lite;` 变成了 `pub use futures_lite::None;`、并直接删掉了
   `pub use buffex;`。本次因此**没有**采用它的自动修复结果，而是手工合并后重跑
   `--check` 确认全部合规。
3. 设备层只覆盖「借用」形态（与 `buffex_tokio_adapt` 的设备层一致）；若以后要支持
   `futures_io` 那族 trait，由于孤儿规则禁止 blanket 桥接，需要平行出一族适配器。
