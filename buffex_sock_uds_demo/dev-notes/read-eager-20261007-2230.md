# 读语义反转：从「填满环段才交付」到「有数据就交付」

日期：2026-10-07 22:30
涉及：`tests/read_semantics_.rs`、`Cargo.toml`（两个适配器改走本机路径）
上游：`buffex_tokio_adapt/dev-notes/local-pump-and-eager-read-20261007-2230.md`、
`buffex_compio_adapt/dev-notes/close-detach-and-eager-read-20261007-2230.md`

## 1. 本仓原先钉住的语义

`tests/read_semantics_.rs` 是本仓最重要的发现之一：两个适配器的读泵都以「**一个可写环段
被填满**」为一次搬运的终点（`move_items_from_input_async` 的上限即段长）。因此设备上只有
`chunk` 字节、而环段还有 `ring_cap - chunk` 字节空位时，`read_async` 会一直 park 到「段
填满」或「设备结束」——**不会**先把已有数据交出来。RTT 用例把 `ring-cap` 钉成 `chunk`
正是为了绕开它。

文件里当时就写明了判据：「若将来适配器改成『有数据就交付』，本文件的
`*_does_not_deliver_*` 用例会失败——那正是提醒：RTT 的 `ring-cap == chunk` 约束可以放宽。」

## 2. 为什么现在必须放宽

`smux_v1_sock_demo`（真实 TCP 上的 mux 互通）需要「请求 / 应答」：握手帧只有几十字节，
而它的 ring-cap 是 256 KiB。旧语义下握手必然静止——对端在等应答，本端在等段填满。
适配器两边因此都改成了「设备给多少就提交多少」（tokio/smol 保住零拷贝，compio 用一次
额外拷贝换掉丢弃未完成设备读的风险）。

## 3. 本次改动

* `tokio_read_does_not_deliver_partial_segment_` → **`tokio_read_delivers_partial_segment_`**：
  环容量 64 KiB、只写 4 KiB 且保持连接，现在必须在窗口内读满（旧断言是「必须超时」）。
* `compio_read_does_not_deliver_partial_segment_` → **`compio_read_delivers_partial_segment_`**：
  同上。
* 文件头与逐条文档注释改为「当前语义：有数据就交付」，并保留「历史」一节说明旧语义与
  它当年的规避手段。
* `Cargo.toml`：两个适配器改走**本机同级路径**（改动还没推到 gitee），否则本仓的特征
  测试会与实现不符。

## 4. 结果

`cargo test --offline --test read_semantics_`：**5/5 通过**
（`tokio_read_delivers_when_ring_equals_message_`、`tokio_read_delivers_partial_segment_`、
`tokio_try_read_delivers_partial_segment_`、`compio_read_delivers_when_ring_equals_message_`、
`compio_read_delivers_partial_segment_`）。

## 5. 影响

* RTT / benchmark 的 `ring-cap == chunk` 约束不再是正确性前提，只是性能调优点；
* 本仓 `src/pump.rs` 的 `pull` 仍然用 `Demand::at_least(1)` 借段，与新语义一致，无需改动。
