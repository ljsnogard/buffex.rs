# `buffex_tokio_adapt` 定位重置：从「调用方 spawn 的泵」到「按需驱动的 TrBuffRead / TrBuffWrite」

日期：2026-10-01 04:24
涉及：`buffex_tokio_adapt` 全 crate（`src/read_.rs`、`src/write_.rs`、`src/shared_.rs`、
`src/lib.rs`、`tests/pump_.rs`、`Cargo.toml`、`Cargo.lock`）
前置：`buffex` 的 `dev-notes/ring-shared-20260929-2109.md` §9、§10.2（人类对该 crate 定位的纠正）

## 1. 目标与结论

**目标**：把任意 `tokio::io::{AsyncRead, AsyncWrite}` 接上 `buffex` 的 `ring`，产出实现
`TrBuffRead` / `TrBuffWrite` 的对象。

**结论**：`buffex` 侧**不需要任何新 API** 就能做；缺的都在适配器 crate 内部。落地形态定为
**「按需驱动、不 spawn」**（与 `buffex_iroh::IrohReader/IrohWriter` 同构）：

* `BuffRead`：设备 → 环，实现 `TrBuffTryRead` + `TrBuffRead`；
* `BuffWrite`：环 → 设备，实现 `TrBuffTryWrite` + `TrBuffWrite`；
* 不 spawn 任何任务；`try_*` 同步推一轮，`*_async` 边等边推，收尾用 `flush_async` /
  `close_async`。

## 2. 为什么不做「端实现 waker、构造环时装进去自动搬运」

这是人类最初的设想（README 旧版与新版的差异）。按当前 `ring` 的 API **做不到**：

| 钩子 | 给端什么 | 能否搬运 |
| --- | --- | --- |
| `TrProducerWaker::init_async(&mut self, ring: &'f mut W)` / `TrConsumerWaker` 同名 | 构建期一次性的 `&'f mut Ring` | ✗ 生命周期只覆盖构建期；`Ring::try_new` / `new_unchecked`（同步构造）根本不调用它 |
| `wake(&self, state: &RingState)` | 只有状态字 | ✗ |
| `TrPark::park_async(&self, demand, state)` | 只有 `Demand` 与状态 | ✗ |

即**端既没有段、也没有环**，只能当被动等待者；真正搬运数据的必须是另有环视图的一方。
可选路线（`ring-shared` 笔记 §10.2 的 A / B / C）都需要先改 `buffex` 的 trait 形状，本轮
**不选**：`Ring::split_unchecked` 已经把「可 `'static` 持有的半部」给了出来，够用了。

## 3. 为什么不做「内部 spawn 的后台泵」

**实测证据**（本轮的编译期探针，`cargo check` 断言）：

| 探针 | 结论 |
| --- | --- |
| `require_send(&RingWriter<Arc<Ring<…>>, …>)` / `require_send(&RingReader<…>)` | **通过**——半部本身 `Send` |
| `require_send(&RingWriter::write_async(&mut tx, &demand))` / `RingReader::read_async(…)`（具体类型下的 future） | **通过** |
| 把「设备 → 环」的搬运循环放进 `tokio::spawn` | **失败**：`lifetime bound not satisfied` + `could not prove {async block}: Send`（rustc issue #100013，`TrPark::ParkAsync` 是 GAT，GAT 投影不传递 auto trait） |

后台泵因此只能落在 `spawn_local`（要求调用方在 `LocalSet` 上下文）上。按需驱动没有这个
包袱，也不额外要求调用方的执行体形态。

## 4. 落地形态

### 4.1 两个适配器 + 共用内核

`src/shared_.rs` 放两侧共用的东西（`lib.rs` 只做逐项导出，不用 `*`）：

* `CoreOf<R, S, A>`：`dev_`（设备）、`ring_`（容器）、`rx_`/`tx_`（两半）、`eof_`、`err_`；
* `RingBuf<A> = Box<[MaybeUninit<u8>], A>`、`SharedRing<B, A> = Arc<Ring<B, u8>, A>`；
* `alloc_ring_(cap, alloc)`：用**调用方给的分配器**分配缓冲本体与 `Arc`，并做容量校验；
* `split_ring_(ring)`：`unsafe { Ring::split_unchecked(ring) }` 的安全封装——容器是**刚刚
  创建**的 `Arc`，无第二句柄、无 `Weak`，两个半部只在同一个适配器内核里成对存活；
* `InvalidCapacity`：容量越界的构造错误（实现 `Display` + `core::error::Error`）。

### 4.1.1 分配点抽象成 `AllocatorConfig`（人类要求，两轮迭代）

**第一轮**（人类）：凡是用到 `Arc` / `Box` 等智能指针的地方都要走 `allocator_api`，
把分配器暴露给上层、默认 `Global`。
**第二轮**（人类）：不要只给**一个**分配器参数，要把「哪儿需要分配器、约束是什么」
提取成一个 **allocator config trait**，让调用方**逐点**配不同的分配器，并提供一个默认实现。

落地形态（`src/alloc_.rs`）：

```rust
pub trait AllocatorConfig: Clone {
    type RingBodyAlloc: AllocatorClone;     // 环的缓冲本体 Box<[MaybeUninit<u8>], _>
    type RingSharedAlloc: AllocatorClone;   // 装环的 Arc<Ring<…>, _>

    fn ring_body_alloc(&self) -> Self::RingBodyAlloc;
    fn ring_shared_alloc(&self) -> Self::RingSharedAlloc;
}

pub struct DefaultAllocatorConfig;   // 四点全 Global，提供给大多数调用方
```

适配器把它作为泛型参数 `C`：

* `BuffRead<R, C = DefaultAllocatorConfig, S = SharedRingOf<C>>`
* `BuffWrite<W, C = DefaultAllocatorConfig, S = SharedRingOf<C>>`
* 构造：`try_new(dev, cap, cfg)`
* 配置里的关联类型摊成具体类型：`RingBufOf<C> = Box<[MaybeUninit<u8>], C::RingBodyAlloc>`、
  `SharedRingOf<C> = Arc<Ring<RingBufOf<C>, u8>, C::RingSharedAlloc>`。

配置只在**构造期**用到（造环：缓冲本体 + `Arc` 各要一个分配器克隆），因此不必存进
适配器；`AllocatorConfig: Clone` 的要求正来自那两次克隆。
（§4.1.3 之后两侧都是零拷贝，配置里也就只剩这两个分配点。）

实施中踩到三个 toolchain / 类型系统细节，记下来免得后人重踩：

1. **`Arc<T, A>: Clone` 要求的是 `A: AllocatorClone`，不是 `A: Allocator + Clone`。**
   本 toolchain（nightly 2026-09-04）的 std 里写的是
   `impl<T: ?Sized, A: AllocatorClone> Clone for Arc<T, A>`（`AllocatorClone: Allocator + Clone`
   是 `core::alloc` 里的 marker，`Global` 有实现，但**标准库不会从 `Clone` 自动推导**）。
   只写 `Allocator + Clone` 会得到 `Arc<…>: Clone is not satisfied`，而 `Ring::split_unchecked`
   恰恰要求容器 `Clone`。⇒ 四个关联类型的约束都用 `core::alloc::AllocatorClone`，
   调用方需 `#![feature(allocator_api)]`（测试与 doctest 都已加上）。
2. **`Ring` 含 `PhantomPinned`，于是 `BuffRead`/`BuffWrite` 默认 `!Unpin`。**
   适配器自身不依赖固定地址（环由 `Arc` 分配、地址稳定，代码里从不把 `Ring` 按值搬出
   堆指针），因此显式 `impl Unpin`，让调用方能 `&mut` 使用、也方便写测试助手。
3. **投影类型不要出现在「需要类型推断」的函数签名里。**
   最初把 `split_ring_<C>(ring: SharedRingOf<C>)` 写成只泛型于配置 `C`，结果
   `let (tx, rx) = split_ring_(ring.clone());` 报 `E0283 type annotations needed`
   ——返回类型里的 `<C as AllocatorConfig>::RingBodyAlloc` 与实参里的投影对不上，
   编译器推不出 `C`。改成泛型于**具体类型** `split_ring_<B, A>(ring: Arc<Ring<B, u8>, A>)`
   后推断正常（helper 只在有具体值时被调用，本来也不需要知道配置类型）。

中转缓冲现在也走配置（`Vec<T, A>` 经实测在本 toolchain 可用：`new_in` / `resize` /
`truncate` 都 OK），不再是第一轮那种「内部细节、固定 `Global`」。

### 4.1.2 第三轮：试着去掉中转缓冲，结果发现上游死循环（人类提问）

**人类的疑问**：数据在设备与环之间为什么还要经 `Vec` 中转？`abs_buff` 不是已经有
`move_items_from_input_async` / `move_items_into_output_async` 专门做「段 ↔ TrInput /
TrOutput」吗？

**结论：写向能去掉，读向暂时不能。**

* 写向（环 → 设备）：`move_items_into_output_async` 直接可用。段直连之后
  `pump_` 只剩「借读段 → 交给设备 → drop 提交」三步，`forward/refill/make_room`
  那一整套中转状态机（以及它带来的死锁陷阱）全部删掉。已改成零拷贝。
* 读向（设备 → 环）：**`TrBuffSegmMut::move_items_from_input_async` 在设备返回 0 字节
  时会死循环**。定位过程：
  * 症状：`read_async` 在空设备（EOF）上永久挂住；`try_read` 的同步一轮也会挂。
  * 最小复现（不经过本 crate 的适配器）：造一个 256 字节的环，借一个写段，
    和 `tokio::io::empty()` 调 `move_items_from_input_async(.., &Demand::no_more_than(room))`
    —— 打印 `room=256` 之后没有任何输出。
  * 根因在 `abs_buff` 的**外层包装** `segm_mut_move_items_from_input_async_`：
    内层 `segm_mut_input_async_` 在设备读返回 0 时正确地返回 `Left(0)`，但外层拿到
    `pick_left() == Some(0)` 后 `c += 0`、`c >= max` 不成立，于是 `continue` ——
    既没有错误可以终止，也没有进度可以脱离，形成忙循环。
  * 附带发现：即使设备不 EOF，只要它一次给不满整段，外层也会在下一次迭代遇到
    「设备暂时没数据」而挂住；也就是说这条路径要求「设备要么一次填满整段、要么给出
    终止性错误」，与真实的 socket / duplex 的短读语义不符。
  * 处置：**读向保留中转缓冲**（先把设备数据整块读进复用缓冲、再逐段拷进环：
    一次 `read` 完整完成后才写环，EOF 由 `read` 返回 0 直接识别，绕开那段死循环）。
    已在 `AllocatorConfig` 里保留独立的 `ReadStageAlloc` 项，并在模块文档里写明原因。

**同时修正的一个测试写法**：取数不要用 `at_least(剩余量)`。`ring` 的
`try_read_internal_` 在「写端未关闭且可读量不足下限」时返回 `Drained` 而不是给出部分
数据（这是有意的语义），因此按「还差多少」当下限会让调用方在短读场景下永久等不到段。
测试助手改成 `at_least(1)` 拿「当前就绪的」、自己按需截断。

### 4.1.3 上游更新 `e4092c8` 之后：读向也做成零拷贝

`abs_buff` 的 `e4092c8 Fix a bug in segm_mut_input_async_ which may cause deadloop`
把那个静默死循环换成了**断言**：

```rust
if let Some(cc) = x.as_ref().pick_left() {
    assert!(*cc > 0 || x.contains_right());   // 「返回 0 且无错误」= 违反契约
    segm.offset_ += *cc;
    c += cc;
}
```

契约因此明确了：**设备返回 0 个必须带上错误**。tokio 的 `AsyncRead` 用「读到 0」表示
EOF，所以需要一层翻译：

| 设备结果 | 翻译成 |
| --- | --- |
| `n > 0` | `Left(n)` |
| `n == 0`（EOF） | `Right(Closing)`（`Closing` 是终止性标签，上游据此收尾） |
| IO 错误 | 原样带标签传播 |

**这层翻译最终落在设备适配器 `abs_buff_tokio_adapt::ReadAsInput` 里**（见该 crate 的
dev-notes `read_as_input-20261001-0632.md`）：那里同样违反了这个契约，修好之后
`buffex_tokio_adapt` 里临时加过的 `EofInput` 包装层就删掉了——EOF 的处理位置收敛到一处。
本适配器只负责把 `Closing` 标签识别为「设备正常结束」：置 EOF 标志而**不**记成设备错误
（否则 `take_error()` 会把正常 EOF 报成错误）。

于是读向也变成零拷贝：借到环的写段 → `move_items_from_input_async` → drop 提交。中转
缓冲、`STAGING_CHUNK`、`alloc_cfg_` 字段与 `ReadStageAlloc` 分配点全部删掉；
`AllocatorConfig` 收敛为两个分配点（环体、装环的 `Arc`）。

新增回归用例 `buff_read_survives_short_reads_`：一个每次最多给 7 字节的设备喂 300 字节、
环容量 64——正是上游过去死循环的触发条件（短读 + 末尾 0 字节），现在要求「字节不乱序
不丢失 + 终止原因是 `Closing` + `take_error()` 为空」。

### 4.2 入向 `BuffRead`

* 实现 `TrBuffTryRead<u8>`：`SegmRef = RingSegmRef<'f, RingBuf, u8>`、`Err = ConsumerError<usize>`；
  实现 `TrBuffRead<u8>`：`ReadAsync = BuffReadOpAsync<'f, 'f, R, S>`（`gen_may_cancel_future`
  生成，可 `may_cancel_with`）。
* `try_read`：`poll_once(self.pump_())` 同步推一轮 → `rx_.try_read(demand)` → EOF 合成。
* `read_async`：循环「`pump_().await` → `rx_.try_read`；`Drained` 则 `rx_.read_async(demand).await`」。
* EOF 合成：设备结束（EOF 或错误）且**环读空**时，把 `ConsumerError::Drained` 改写成
  `ConsumerError::Closing`。

### 4.3 出向 `BuffWrite`

* 实现 `TrBuffTryWrite<u8>` / `TrBuffWrite<u8>`（`SegmMut = RingSegmMut<'f, RingBuf, u8>`）。
* 状态：`pending_`（中转缓冲，`Vec<MaybeUninit<u8>>`）、`sent_`、`closed_`、`err_`。
* 三个原语，**顺序不可反**：

  | 原语 | 做什么 | 关键约束 |
  | --- | --- | --- |
  | `forward_pending_` | 把 `pending_` 写给设备 | 只动本对象手里的数据，写多少算多少 |
  | `refill_from_ring_` | 从环借段、拷进 `pending_`，drop 段提交 | **只在 `pending_` 已写净时调用** |
  | `make_room_sync_` / `make_room_async_` | 先冲、再补；返回「`pending_` 是否为空」 | **只有为空才代表环空间被释放** |

* `write_async` 每轮先 `make_room_async_().await`，再尝试借段；`flush_async` 循环冲到「环空
  且中转写净」；`close_async` 循环冲净后再 `shutdown`。

## 5. 实施中踩到并修掉的四个坑

1. **`Cargo.lock` 钉的 `abs_buff` 太旧（`14f204b`）**，而 `buffex` 用的是 `de05cd7`：
   编译直接失败在 **`buffex` 本体**（26 个 `mismatched types` + `no_more_than` 不存在）。
   `cargo update -p abs_buff` 后 `buffex` 即通过。
2. **同步 throwaway poll 会丢数据（写侧）**：最初 `try_write` 用 `poll_once(flush_pending_())`
   推一轮，而 `flush_pending_` 会先把环段搬进 `pending_`（`advance_read` 已提交）再 await
   设备；future 被 poll 一次就丢弃时，那批字节既不在环里也没到设备。
   **修法**：拆成「先冲 `pending_`，写净后才补货」，并把同步轮与异步轮统一到
   `make_room_*` 上。
3. **`write_async` 会死锁**：环被填满后 park 等空间，而没有任何一方在往设备写（设备写只
   发生在 `flush_pending_` 里）。**修法**：`write_async` 每轮先 `await` 一次
   `make_room_async_`，让「调用方持续借段」这件事本身就把数据推向设备。
4. **`close_async` 只冲一遍**：`flush_pending_` 在设备背压时提前返回，于是 `shutdown` 时环里
   还剩几千字节（实测：4096 字节只送达 256）。**修法**：循环到「环空 + 中转写净」再
   `shutdown`。

## 7. 遗留

* **`Ring` 仍缺 `close`**：目前靠适配器自己记 EOF 再合成 `Closing`；若将来 `ring` 补上
  关闭入口（置 `PRODUCER_CLOSED` 并唤醒对端），这里的合成逻辑可以退化成直接转发。
* **`tokio::spawn`（多线程）仍不可用**（§3），属依赖链上的已知约束；要走 S1–S3 任一方案
  得同时改 `abs_cancel` / `gen_mcf2` 的形状。
* 两侧都已零拷贝（§4.1.3），EOF 翻译也收敛到了 `abs_buff_tokio_adapt` 一处。上游若
  愿意让「0 且无错误」直接等价于 EOF（tokio 惯例），那一层翻译同样可以删掉。
* `BuffReadBuilder` / `BuffWriteBuilder`（自定义容器或缓冲本体）**未做**：当前只提供
  `try_new(dev, cap)`，容器固定 `Arc<Ring<Box<[MaybeUninit<u8>]>>>`。
* 上一版「调用方 spawn 的泵对象」骨架（`ReadToRing` / `RingToWrite`）已 `git stash`
  保存（`stash@{0}`，提交点为 `4b2cbf1`），仅作历史参考，与本设计不兼容。
