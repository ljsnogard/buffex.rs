# 出向泵 100% CPU 空转：定位与修复

`buffex_tokio_adapt/README.md`（顺手清理过时描述）
前置：`buffex_uds_comp_experiment/dev-notes/experiment-20261002-0058.md` §3.1（100% CPU 现象）、

## 1. 现象与触发条件

`buffex_uds_comp_experiment` 观察到 tokio 侧进程「utime/stime 每秒都在涨」，即 100% CPU
空转。触发条件是**设备已经不可能再接受字节、但环里还有数据**：对端退出（`EPIPE`）、
设备返回 0（违约）等。

用实验项目的真实二进制做的进程级对照（`rtt-server` 收一条 64 KiB、对端随后关闭，
3 秒观察窗，8 轮）：

| 版本 | 自然退出 | 单轮 CPU | 结论 |
| --- | --- | --- | --- |
| 修复前 | **0 / 8** | **2.99 ~ 3.01 s / 3 s** | 99.9% CPU 空转，永不返回 |
| 修复后 | **8 / 8**（rc=1，21 ms） | ~0.00 s | 如实报错：`Closing` + `BrokenPipe` |

修复后的真实报错（`peer_tokio` 的 stderr）：

```
peer_tokio 失败：tokio 写端 flush 失败：Closing；设备错误：
  Os { code: 32, kind: BrokenPipe, message: "Broken pipe" }（Propagated）
```

## 2. 根因链

四处叠加，前两处是本次报告的现场，后两处是同一类问题的其它入口。

### 2.1 「有进展」的判据错了：`Both(0, err)` 也含 `Left`

修复前 `BuffWrite::pump_` 的收尾：

```rust
if moved.contains_left() || !moved.contains_right() {
    return true;                       // ← Both(0, err) 也满足 contains_left()
}
if let Option::Some(err) = moved.pick_right() {
    self.err_ = Some(take_io_err_(err)); // ← 于是这行根本不会执行
}
false
```

`anylr::SomeOf` 的 `Both(n, err)` **同时**含 `Left` 与 `Right`。设备写失败、
一个字节都没出去时，上游给回的正是 `Both(0, err)`：`contains_left()` 为真 ⇒
`pump_` 报「有进展」且**不记错误**。段按已搬出量 0 提交（`advance_read(0)`），
环里数据一个不少。这是「空转 + 吞错」的根。

### 2.2 收尾循环把「有进展」当唯一出口

```rust
while buf_write.pump_().await {}      // pump_ 永远返回 true
if buf_write.err_.is_some() { ... }   // 错误已被 2.1 吞掉，永远 false
if ring.data_size() == 0 { ... }      // 数据一个字节都没减少，永远 false
```

⇒ 紧循环，且循环体内没有任何 `await` 会真正 park（设备 `Ready(Err)` 立即完成），
**连 `tokio::time::timeout` 都无法插进来**。`close_async` 的循环同构。

### 2.3 设备在非空缓冲上返回 `Ok(0)` 时，上游自己会空转

`abs_buff` 的输出搬移内层（`segm_ref_output_async_`）看到 `Ok(0)` 就退回
`Left(0)`，外层（`segm_ref_move_items_into_output_async_`）拿不到错误便 `continue`
再试一次——同样是**不让出执行体的紧循环**，且位置在我们拿不到控制权的地方
（`await move_items_into_output_async(..)` 永不返回）。tokio 只在**空缓冲**时允许
`Ok(0)`；非空缓冲返回 0 属设备违约（`std::io::Write::write_all` /
`tokio::io::AsyncWriteExt::write_all` 对它的处置都是 `WriteZero`）。

### 2.4 收尾循环缺少「零进展」兜底

即使 2.1 修好（错误被记下），只要出现「环非空、无错误、又零字节交付」的组合，
`while pump_().await {}` + 外层 `loop` 仍会空转。

## 3. 技术决策

### 3.1 三条保证（写端）

1. `pump_` 的返回值 = **真的向设备交付了至少 1 个字节**（`n > 0`），与「结果里含
   `Left`」解耦；
2. **任何**带错误的结果都先记进 `err_`（含 `Both(n, err)`）——设备错误不许被吞掉；
3. `flush_async` / `close_async` 在「环非空 + 无错误 + 一整轮零字节交付」时记一条
   `WriteZero`（标签 `WriteErrTag::Unknown`）并**终止**，把控制权还给调用方。

第 3 条选「零进展即终止」而不是「重试 N 次」或「让出执行体再试」：`pump_` 只在
「环空 / 设备错误 / 零进展」三种情况返回 false，前两种都已各自处理，剩下的第三种
（设备既不收也不报错）不会自愈，重试只是换一种方式烧 CPU。

### 3.2 设备边界包装 `ZeroWriteAsErr`

针对 2.3：在**设备边界**（`WriteAsOutput` 之外）套一层私有包装，把非空缓冲上的
`Ok(0)` 翻成 `io::ErrorKind::WriteZero`。这样违约设备变成「终止性设备错误」，
适配器按 3.1 的第 2、3 条正常收尾；上游紧循环失去输入，问题闭环。

不选「重写搬运、绕开 `move_items_into_output_async`」的原因：那条路径的
**部分交付逐段提交**语义（写多少提交多少、drop 段推进 offset）正是零拷贝与
不丢字节的基础，自己重写等于把 `abs_buff` 的段语义再实现一遍，收益不抵风险。
包装只借用设备、不改变 `poll_*` 的调用方式，合法设备的开销为零。

### 3.3 为什么不在上游改

- 2.1 / 2.2 是**本 crate 自己**的判据与循环，改在这里就能闭环，不必等上游发版；
- 2.3 的紧循环确实在 `abs_buff` 里，但「设备违约」这一判定放在**设备适配层**
  最自然（本 crate 与 `abs_buff` 之间只隔一层 `WriteAsOutput`），且不改上游的
  段语义；上游若要收，建议把 `Ok(0)` 直接当 `WriteErrTag::Unknown` 处理。

## 4. 验证

### 4.1 新增回归用例（`tests/no_spin_.rs`，均带中文文档注释）

| 用例 | 覆盖 |
| --- | --- |
| `flush_does_not_spin_on_zero_bytes_with_error_` | `Both(0, BrokenPipe)` ⇒ `flush_async` 有界返回且错误可取回 |
| `close_does_not_spin_on_zero_bytes_with_error_` | 同上，走 `close_async` |
| `partial_delivery_still_records_device_error_` | `Both(n > 0, err)` ⇒ 错误照记、不反复重试 |
| `flush_does_not_spin_on_zero_progress_without_error_` | 非空缓冲 `Ok(0)` ⇒ `WriteZero` 且有界返回 |
| `close_records_broken_pipe_instead_of_spinning_` | 真实 `tokio::io::duplex` 对端退出 ⇒ `BrokenPipe` 可取回 |

**判定手段的关键取舍**：这些设备都是「立即 `Ready`」的，空转时循环不让出执行体，
`tokio::time::timeout` **根本不会触发**（第一版用例就因此把测试挂死 10 分钟）。
改成设备侧**调用次数护栏**：超限即 panic，「空转」于是表现为测试失败而不是挂死。
（曾为此给 dev-dependencies 加 `tokio/time`，确认 timeout 无效后已撤销该改动。）

修复前跑同一套用例：**5 / 5 失败**（`空转：…::poll_write 被调用 9 次（上限 8）`）；
修复后 **5 / 5 通过**。

## 5. 读侧为什么不在本次改动范围

读了 `read_.rs` 的 `pump_` 与 `buff_read_async_`：读侧每一步都以**设备读**为 await
点（`ReadAsInput` 把「读到 0」翻成带 `Closing` 的终止性错误，`abs_buff` 内层据此
`return`），不存在「立刻 `Ready` 且零进展」的循环形态；`rx_.read_async` 在环空时
park 在等待槽上（`buffex` 自带的 `read_async_parks_*` 用例覆盖）。因此本次不动读侧。

## 6. 遗留与待决策

1. **入向交付语义（本 crate 的产能瓶颈，非本次范围）**：读侧泵要把一个写段填满
   （或设备 EOF / 出错）才提交进环，小消息 + 对端不再补数据时会停在「等段填满」——
   乒乓式请求/应答必须「环容量 = 消息长度」才能跑通（实验 §3）。要放宽它需要
   「有数据就交付」的搬运语义（或在 `buff_read_async_` 里把「设备可读」与
   「环可读」做 `select` 式交错），属**行为/约定层面的改动**，按纪律需团队先决策。
2. **上游 `Ok(0)` 空转**：本次在设备边界兜住了；根治建议放 `abs_buff`
   （`segm_ref_*output*` 把 0 字节且无错误判成终止性错误）。
3. **`close_async` 目前忽略取消令牌**（`_cancel`）：与 `AGENTS.md` §4「异步方法不得
   假定调用方不会取消」存在偏离，但「关闭必须完成」本身也有语义权重，建议单独讨论
   后再定，不在本次改动内。
4. `Both(0, err)` 曾经吞掉的错误现在会经 `take_error` 暴露，**对调用方是可见行为
   变化**（以前是「静默 + 空转」，现在是「报错 + 返回」）；两个对端的 benchmark 主体
   本来就把 `Err` 当失败处理，实验项目 21 条用例全通过，未产生新的兼容问题。
